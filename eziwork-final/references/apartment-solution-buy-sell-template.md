# 아파트 솔루션 BUY·SELL 리포트 템플릿 명세

## 1. 템플릿 목적

아파트 상담 고객을 `BUY`와 `SELL` 두 유형으로만 구분합니다. 입지·상품·실거래·현재 공개호가·비교단지 분석은 공통으로 만들고, 마지막 판단과 행동 기준만 고객 유형에 맞게 분기합니다.

- `BUY`: 얼마까지 검토하고, 무엇을 확인하며, 어떤 조건에서 매수를 중단할지 결정합니다.
- `SELL`: 얼마에 출시하고, 어떤 반응을 측정하며, 언제 어느 구간으로 조정할지 결정합니다.

템플릿의 시각적 기준은 `[아파트솔루션] 반포자이_2305 (1).pdf`의 연구보고서형 편집 체계입니다. 원본의 페이지를 복제하지 않고 다음 특징을 재사용합니다.

- 넓은 흰 여백과 얇은 검은 구분선
- 파란색 대분류와 검은색 결론형 제목
- 설명형 본문 뒤에 지도·사진·표·차트를 배치하는 흐름
- 회색 제목 바가 있는 근거표
- 페이지 하단의 자료·기준일·브랜드·쪽번호

## 2. 고정 페이지 구조

기본 리포트는 10페이지입니다. 실제 근거량에 따라 부록을 추가할 수 있지만 공통 분석과 유형별 판단 순서는 바꾸지 않습니다.

|---:|---|---|---|

| 2 | 입지 가치 | 교통·업무지구 접근성, 실제 이동 시 확인할 한계 | 정적 지도, 소요시간 표 |
| 3 | 생활 가치 | 학교·학원·생활상권·공원, 고객 우선순위와 현장 확인사항 | 교육조건 표, 생활요소 카드 |

| 9 | 유형별 판단 | BUY 또는 SELL의 판단 단계와 다음 행동 | 의사결정표, 한눈에 설명 |

## 3. 공통 데이터 모듈

### 3.1 단지 프로필

필수 필드:

- 단지명, 주소, 준공연도, 세대수, 동수·최고층
- 용적률·건폐율, 시공사, 면적 구성, 주차대수
- 단지 또는 개별 매물 이미지
- 단지를 설명하는 핵심 특징 2개

기본 출처:

- 건축물대장·공동주택관리정보·지자체 또는 단지 공식자료: `S1`
- 소유자·중개사 현장 확인자료: `S3`

### 3.2 입지·생활

필수 필드:

- 역·버스·간선도로까지의 실제 이동 경로
- 주요 업무·생활권 소요시간
- 학교 배정과 통학로, 생활상권, 병원·공원
- 지도 캡처의 제공자, 검색 위치, 캡처일

수집 방식:

1. 지도 서비스에서 대상 단지를 검색합니다.
2. 검색창·목록·조작 버튼을 제외하고 지도와 제공자 표기만 남겨 정적 이미지로 저장합니다.
3. 직선거리와 예상시간을 확정적 사실처럼 쓰지 않습니다.
4. 실제 출입구, 신호, 경사, 야간 동선은 현장에서 확인합니다.

### 3.3 실거래

기본 출처는 국토교통부 실거래가 공개자료 `S1`입니다.

- 동일 단지·동일 거래유형·동일 전용면적을 우선합니다.
- 계약일, 가격, 층, 취소·해제 여부를 보존합니다.
- 진행 중인 월과 완결월을 구분합니다.
- 건수·중위값·최저·최고의 표본 수를 함께 표시합니다.
- 누락 기간을 보간하지 않습니다.

### 3.4 현재 공개매물

기본 출처는 네이버페이 부동산의 사용자 실행형 제한 조회 `S2`입니다.

- 한 단지·한 면적의 판단에 필요한 매물만 확인합니다.
- 조회시각, 거래유형, 면적, 가격, 층, 방향, 수리·입주조건을 기록합니다.
- 중복 중개 매물은 동일 매물로 확인된 경우에만 묶습니다.
- 공개호가를 실거래나 역사적 시세로 바꾸어 표현하지 않습니다.
- 로그인·CAPTCHA·차단을 우회하거나 전체 사이트를 수집하지 않습니다.

### 3.5 비교단지

선정 우선순위:

1. 동일 생활권
2. 동일 거래유형과 유사 전용면적
3. 유사 준공연도와 세대 규모
4. 실제로 고객이 대체 선택할 수 있는 거리

선정 이유와 제외 이유를 내부 QA 기록에 남깁니다. 상품 차이는 가격 보정의 확정값이 아니라 설명해야 할 조건으로 사용합니다.

## 4. 가격 판단 모듈

기본값은 하나의 적정가를 선언하는 방식이 아닙니다.

1. 동일 단지·동일 면적의 유효 실거래 범위를 중심 근거로 둡니다.
2. 현재 공개호가는 매도자의 현재 희망조건과 경쟁 구간으로 분리합니다.
3. 비교단지는 대체 선택지와 상품 차이를 설명하는 보조 근거로 둡니다.
4. 층·향·조망·수리·점유·인도조건을 확인하지 못하면 가격 가산·차감을 확정하지 않습니다.

별도 적정가 공식은 다음 조건을 모두 충족할 때만 선택 모듈로 추가합니다.

- 공식의 명칭과 목적이 명확할 것
- 모든 입력값의 원자료와 기준일이 있을 것
- 계산식이 재현될 것
- 적용 배수·할인율의 선택 이유가 있을 것
- 결과를 감정가나 확정 시세로 표현하지 않을 것

## 5. BUY 판단 모듈

고정 질문:

> 검토가격이 최근 체결가격과 현재 공개호가에서 어느 위치이며, 어떤 조건을 확인한 뒤 얼마까지 협상할 것인가?

필수 출력:

- 검토가격과 실거래 기준의 차이
- 실제 대체 가능한 매물
- 개별 매물의 가산·차감 조건
- 취득·수리·금융비용을 포함한 총비용
- 협상 시작점, 상한, 매수 중단조건

문장 구조:

1. `검토가격은 [가격 위치]입니다.`
2. `[가격 차이]를 설명할 [조건]을 확인해야 합니다.`
3. `[대안]을 우선 협상근거로 사용합니다.`
4. `[상한 또는 중단조건]을 넘으면 검토를 보류합니다.`

## 6. SELL 판단 모듈

고정 질문:

> 현재 시장에서 어느 가격으로 출시하고, 어떤 시장 반응을 기준으로 언제 조정할 것인가?

필수 출력:

- 출시가격의 실거래·공개호가 내 위치
- 직접 경쟁하는 현재 매물
- 가격 차이를 설명할 상품·계약 조건
- 문의·방문·제안가격 측정기간
- 유지·조정·협상 가격 구간
- 잔금·인도조건과 희망 순수령액

문장 구조:

1. `출시가격은 [가격 위치]입니다.`
2. `[경쟁 매물]과의 차이를 [상품 조건]으로 설명해야 합니다.`
3. `[기간] 동안 [문의·방문·제안]을 기록합니다.`
4. `반응이 [기준]보다 낮으면 [조정 구간]을 다시 검토합니다.`

## 7. 문장·어조 규칙

- 고객이 직접 읽는 설명형 문장으로 씁니다.
- `확인됩니다`, `비교할 수 있습니다`, `추가 확인이 필요합니다`를 기본 어미로 사용합니다.
- 관찰된 사실, 의미, 미확인사항, 다음 행동의 순서로 씁니다.
- `고객에게는 이렇게 설명합니다`, `중개사가 사용합니다`와 같은 내부 문구를 넣지 않습니다.
- `무조건`, `확실한 급매`, `반드시 상승`처럼 결과를 보장하지 않습니다.
- 표와 차트에서 확인할 수 없는 숫자를 본문에 새로 만들지 않습니다.

## 8. 디자인 토큰

- 용지: A4 세로
- 본문 배경: `#FFFFFF`
- 제목 파랑: `#2B66D6`
- 진한 남색: `#0C2E69`
- 본문 검정: `#15191E`
- 표 제목 배경: `#DEDEDE`
- 핵심 강조: `#F06442`
- 본문 크기: 약 8.5~9pt, 행간 1.7
- 제목 크기: 10~13pt, 결론 페이지 31pt
- 일반 페이지의 상단 본문 시작점은 오른쪽 주열에 맞추고, 표·지도·차트는 좌우 전체 폭을 사용할 수 있습니다.
- 페이지마다 좌측 하단 자료, 중앙 하단 브랜드, 우측 하단 쪽번호를 둡니다.
- 실제 건물사진이 없을 때는 다큐멘터리 사진처럼 보이는 이미지를 만들지 않고 단지 일러스트를 사용합니다.

## 9. 신뢰성·배포 기준

실제 고객용 PDF는 다음 조건을 모두 충족해야 합니다.

- 실거래와 현재 공개매물이 서로 다른 근거로 표시됨
- 모든 시점 민감 수치에 출처·기준일·조회조건이 있음
- 원자료, 정규화자료, 제외내역, 취소·중복 처리 기록이 보존됨
- 차트·표·본문·결론이 동일한 정규화 필드를 사용함
- 실제 모드는 기존 근거 감사 결과가 `PASS` 또는 `PASS WITH CONDITIONS`임
- `HOLD`인 경우 고객용 HTML·PDF를 만들지 않음
- PDF 전 페이지에서 한글 깨짐·잘림·요소 겹침·빈 페이지·지도 조작 버튼이 없음

## 10. 실행 방법

동일한 요청 파일에서 고객 유형만 선택합니다.

```powershell
python build_apartment_solution_report.py demo-request.json --customer-type BUY --output BUY/report.html --audit-output BUY/evidence-audit.json
python build_apartment_solution_report.py demo-request.json --customer-type SELL --output SELL/report.html --audit-output SELL/evidence-audit.json
```

생성된 HTML은 기존 `render_report.mjs`를 이용해 PDF로 출력합니다.
